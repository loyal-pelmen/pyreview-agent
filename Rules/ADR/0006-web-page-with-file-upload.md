# 0006 — Страница с загрузкой файла вместо ревью PR в GitHub

Тип: решение
Статус: принято, 29.10.2026

## Контекст

Первая постановка — агент читает PR в GitHub и публикует обзор ([записи 0004](0004-one-review-with-line-comments.md) и [0005](0005-github-rest-through-single-client.md)). Владелец уточнил флоу: нужна страница, на которую человек перетаскивает один файл `.py`, бэкенд прогоняет линтеры и логический разбор агентом и возвращает ревью с цепочкой рассуждений, страница их показывает. Хранить ничего не нужно, хостинг кода и PR в задаче отсутствуют.

## Решение

Веб-приложение из двух частей в одном репозитории. Бэкенд — FastAPI: `POST /api/v1/review` принимает `multipart/form-data` с одним файлом, проверяет расширение, размер и кодировку, кладёт файл во временный каталог, собирает агента и отвечает одним JSON; `GET /api/v1/config` отдаёт несекретную часть конфига; `GET /healthz` — живость. Страница — `frontend/index.html`, `styles.css`, `app.js` без фреймворков и сборки, отдаётся тем же приложением через `StaticFiles` с корня, поэтому CORS не нужен. Временный каталог удаляется в `finally`; базы, сессий и файлов на диске вне запроса нет.

Записи 0004 и 0005 заменяются этой. Запись 0003 действует с поправкой: вместо checkout головы PR линтеры работают над временным каталогом с присланным файлом. Запись 0002 действует: бэкенд файлов Deep Agents — `FilesystemBackend` с корнем во временном каталоге и инструментами только на чтение.

## Альтернативы

- **Оставить GitHub-режим вторым входом** — отклонено: два входа удваивают контракт и тесты, а запроса на PR нет. Поток «файл → ревью» внутри не зависит от источника, и источник можно добавить позже отдельной записью.
- **Отдельный сервер статики или фронт на фреймворке** — отклонено: три файла без сборки покрывают задачу, а второй процесс и CORS добавляют только трудностей.
- **Хранить результаты, чтобы показать историю** — отклонено условием владельца: бэкенд ничего не хранит.
- **Принимать текст кода JSON-полем вместо файла** — отклонено: перетаскивание файла — требование флоу, а имя файла нужно линтерам и отображению.

## Последствия

- Зона `github` исчезает; остаются `analysis`, `linters`, `shared`, `entrypoints`. Клиент GitHub, карта строк диффа и идемпотентность по `SHA` не делаются.
- Контракт ответа становится главным артефактом между частями и живёт в `openspec/notes/api-contract.md`; правка контракта затрагивает обе части в одном изменении.
- Файл приходит целиком, поэтому строки находок считаются по файлу, а не по диффу: проверка — «строка в диапазоне файла».
- Повторная отправка того же файла даёт новый анализ: без хранения идемпотентности нет, и она не нужна.
