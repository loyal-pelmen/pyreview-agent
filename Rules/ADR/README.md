# ADR — журнал записей

Каждая задача перед началом работы классифицируется по типу, и на неё заводится запись. Записи заводятся и правятся скиллом `project-docs`, а не вручную. Запись отвечает на вопрос «почему сделано так» и переживает саму задачу.

## Формат

Файл `NNNN-краткое-название.md`, номер четырёхзначный, сквозной по всем типам, не переиспользуется. Первые строки:

```
# NNNN — Название

Тип: решение | фича | баг | рефакторинг | миграция | исследование
Статус: принято | в работе | выполнено | заменено NNNN | отменено, ДД.ММ.ГГГГ
```

Дальше — заголовки того типа, к которому отнесена задача. Набор заголовков обязателен целиком: раздел, по которому нечего сказать, заполняется словом «нет», а не удаляется.

Границы задачи называются всегда, но разделы для них у типов разные: у фичи и бага — «Что не делаем», у рефакторинга — «Что не трогаем», у решения — «Последствия», у миграции — «Совместимость», у исследования — «Ограничения». Пустым этот раздел не бывает: если границу не назвали, задача не разобрана.

Текст записи со статусом «принято» или «выполнено» не переписывается: решение отменяется новой записью, а в старой ставится `заменено NNNN`. Строка `Статус:` — исключение, она актуализируется по факту.

## Типы и их заголовки

| Тип | Внутренние заголовки |
|---|---|
| **решение** | Контекст · Решение · Альтернативы · Последствия |
| **фича** | Задача · Контекст · Что не делаем · Что готово когда |
| **баг** | Симптом · Воспроизведение · Ожидаемое · Точка входа · Что не делаем |
| **рефакторинг** | Цель · Область · Что не трогаем · Что готово когда |
| **миграция** | Старое состояние · Новое состояние · Шаги · План отката · Совместимость · Чек-лист |
| **исследование** | Вопрос · Где смотреть · Что нужно от тебя · Ограничения |

Тип выбирается по тому, что задача меняет: поведение системы — фича; расхождение с ожидаемым поведением — баг; форма кода без изменения поведения — рефакторинг; переход состояния данных, схемы или контура — миграция; ответ на вопрос без правки системы — исследование; выбор между вариантами, действующий дальше, — решение.

## Связь с PR и OpenSpec

Тип задачи и ссылка на запись указываются в описании PR. `design.md` изменения OpenSpec объясняет решения внутри этого изменения и живёт до архива; решение, действующее после архива, переносится сюда записью типа «решение».
