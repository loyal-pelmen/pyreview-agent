# Вспомогательные файлы проекта

Единственный способ заводить и править `Rules/`, `README.md` и `Rules/ADR/`. Вручную эти файлы не редактируются: без классификации задача уходит без границ, а факт, записанный в двух местах, расходится.

## Шаг 0. Прочитай источники

Типы задач и их обязательные заголовки — в `Rules/ADR/README.md`. Нормы проекта — в `Rules/RULES.md`. Эта инструкция их не пересказывает: читай файлы, а не полагайся на память.

Пути даны от корня репозитория.

## Шаг 1. Классифицируй задачу

Отнеси задачу ровно к одному типу: **решение**, **фича**, **баг**, **рефакторинг**, **миграция**, **исследование**. Критерий выбора — в `Rules/ADR/README.md`.

Задача, попадающая под два типа, разбивается на две записи. Классификация делается до начала работы, а не после.

## Шаг 2. Заведи запись

```bash
ls Rules/ADR/[0-9]*.md | tail -1        # последний номер
```

Файл `Rules/ADR/NNNN-краткое-название.md`, номер следующий по порядку, сквозной по всем типам. Шапка — `# NNNN — Название`, затем строки `Тип:` и `Статус:`.

Дальше — заголовки того типа, к которому отнесена задача, все до одного. Раздел, по которому нечего сказать, заполняется словом «нет». Раздел, называющий границы задачи, пустым не бывает.

Добавь строку в таблицу записей в `Rules/ADR/README.md`.

Запись со статусом «принято» или «выполнено» не переписывается — решение отменяется новой записью, а в старой ставится `заменено NNNN`.

## Шаг 3. Обнови задетые документы

Факт живёт в одном месте. Перед тем как что-то записать, проверь по таблице, куда он относится:

| Что записываешь | Куда |
|---|---|
| норму постоянного действия | `Rules/RULES.md`, в свой из пяти разделов; только проверяемое требование |
| требование к системе | `Rules/REQUIREMENTS.md`: код `FR-*` или `NFR-*`, приоритет `M`/`S`, блок приёмки |
| обоснование, альтернативы, разбор задачи | запись в `Rules/ADR/` |
| что система делает и как с ней работать | `README.md` репозитория: цель · что НЕ входит · состав · как работать |
| наличие документа и где какой ответ | `AGENTS.md` — строкой в таблице, без пересказа |
| решение, действующее только внутри изменения | `design.md` этого изменения |

Новых разделов в `RULES.md` и новых типов записей не заводи.

## Шаг 4. Проверь

```bash
grep -rnE "Authorization: Bearer [A-Za-z0-9]|ghp_[A-Za-z0-9]|github_pat_[A-Za-z0-9]|[0-9]{1,3}(\.[0-9]{1,3}){3}" . --exclude-dir=.git --exclude=SKILL.md | grep -vE "127\.0\.0\.1|0\.0\.0\.0" ; echo "код $?"
```

- Ищи по всему дереву от корня репозитория, включая `openspec/`. Код `1` — чисто; код `0` — есть попадания; код `2` — grep не отработал, и это повод перезапустить.
- Токен GitHub, ключ GigaChat и прочие секреты в файлах не появляются: стоят имена переменных или плейсхолдеры вида `<GITHUB_TOKEN>` (`INV-02`).
- Локальные ссылки ведут на существующие файлы.
- Ни один факт не записан дважды: если абзац повторяет другой документ, оставь ссылку.
- Инвариант `INV-*` не изменён. Если задача его ломает — это отдельный PR, в котором записано, почему инвариант больше не нужен.
- Задет `openspec/changes/<name>/` — прогони `openspec validate <name> --strict`.

## Шаг 5. Оформи PR

Первая строка описания — тип задачи и ссылка на запись:

```
**Тип задачи:** фича · [запись 0006](Rules/ADR/0006-….md)
```

В конце — раздел «Что не делаем» с границами из записи. Коммиты и ветки — на английском, императив, gitflow.

## Чего не делает этот скилл

Не пишет код, не коммитит без просьбы, не правит `openspec/config.yaml` и не выполняет действия из раздела «Что не автоматизировать без согласия» в `Rules/RULES.md`.
